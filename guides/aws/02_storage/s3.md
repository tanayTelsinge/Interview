# Amazon S3 — Simple Storage Service
## SAP-C02 Deep Dive

---

## 1. The Problem

Before S3, storing files at scale meant:
- Buying physical servers and maintaining RAID arrays
- No elasticity — you over-provisioned or ran out
- Replication and durability were your engineering problem
- No global access without expensive CDN integration
- Backup/archive required separate tape/disk infrastructure

AWS needed an object store that: never fills up, survives AZ failures automatically, costs fractions of a cent per GB, and integrates with every other service.

---

## 2. What AWS Built

Amazon S3 (Simple Storage Service) is a **regionally scoped, infinitely scalable object store**. It stores objects (files + metadata) in buckets. There is no filesystem hierarchy — only flat key-value storage with "/" as a naming convention.

| Property | Value |
|---|---|
| Max object size | 5 TB |
| Max objects per bucket | Unlimited |
| Max buckets per account | 100 (soft) / 1000 (hard) |
| Max key length | 1024 bytes |
| Max metadata per object | 2 KB (user-defined) |
| Minimum billable object size | 128 KB for IA / 40 KB for Glacier classes |

---

## 3. How It Works

### Object Model

Every S3 object consists of:

```
Bucket: my-company-data
Key:    logs/2024/01/app.log          ← full path is the key
Value:  <binary data up to 5 TB>
Metadata:
  - System: Content-Type, ETag, Last-Modified, Content-Length
  - User-defined: x-amz-meta-project=alpha (up to 2 KB)
Version ID: null (if versioning off) or abc123xyz (if on)
```

### Storage Internals (What AWS Doesn't Publicize)

S3 is built on a custom distributed key-value store. Objects are sharded across many physical servers by hashing the key prefix. Before 2018, using sequential prefixes (e.g., `2024-01-01/`, `2024-01-02/`) caused hotspots because the same shard handled sequential keys — AWS recommended random prefixes. Today S3 auto-partitions on all prefixes, but the old exam questions still appear.

**Per-prefix performance** (current):
- 3,500 PUT/COPY/POST/DELETE requests per second
- 5,500 GET/HEAD requests per second

### Strong Consistency Model (since December 2020)

S3 provides **strong read-after-write consistency** for:
- PUT of new objects
- PUT overwrite
- DELETE
- LIST (eventual in the past, now strongly consistent)

There is **no more eventual consistency window**. This eliminated the classic race condition where a GET immediately after a PUT could return 404.

## 4. Storage Classes

### Full Comparison Table

| Class | Min Duration | Min Size | Availability | First-byte Latency | Use Case |
|---|---|---|---|---|---|
| **S3 Standard** | None | None | 99.99% | ms | Active, frequently accessed |
| **S3 Intelligent-Tiering** | None | None (40KB min charge) | 99.9% | ms–hours | Unknown/changing access patterns |
| **S3 Standard-IA** | 30 days | 128 KB | 99.9% | ms | Infrequent, still needs ms access |
| **S3 One Zone-IA** | 30 days | 128 KB | 99.5% (1 AZ) | ms | Infrequent, recreatable data |
| **S3 Glacier Instant Retrieval** | 90 days | 128 KB | 99.9% | ms | Quarterly access, archive |
| **S3 Glacier Flexible Retrieval** | 90 days | 40 KB | 99.99% | min–12h | Yearly backups, cost priority |
| **S3 Glacier Deep Archive** | 180 days | 40 KB | 99.99% | 12–48h | Long-term regulatory compliance |

### Intelligent-Tiering Tiers

| Tier | Access Pattern | Extra Fee |
|---|---|---|
| Frequent Access | Accessed recently | None |
| Infrequent Access | Not accessed 30+ days | None |
| Archive Instant Access | Not accessed 90+ days | None (opt-in) |
| Archive Access | Not accessed 90–180+ days | None (opt-in, 3–5h retrieval) |
| Deep Archive Access | Not accessed 180+ days | None (opt-in, 12h retrieval) |

Monitoring fee: **$0.0025 per 1,000 objects/month** — not worth it for tiny objects.

| Mode | Flexible Retrieval | Deep Archive |
|---|---|---|
| Expedited | 1–5 min | N/A |

## 5. Versioning and MFA Delete

### Versioning States

```
Bucket versioning states:
  ┌──────────────────┐
  │   Unversioned    │ (default)
  └────────┬─────────┘
           │ Enable versioning
           ▼
  ┌──────────────────┐
  │     Enabled      │ ← Can suspend, cannot go back to unversioned
  └────────┬─────────┘
           │ Suspend
           ▼
  ┌──────────────────┐
  │    Suspended     │ ← New writes get null version ID
  └──────────────────┘
```

When versioning is enabled:
- DELETE creates a **delete marker** (not a real deletion)
- Delete the delete marker to restore the object
- Old versions billed normally — watch your costs

### MFA Delete

Requires MFA device to:
- Permanently delete an object version
- Change versioning state of bucket

```bash
# Enable MFA Delete (only root account can do this via CLI)
aws s3api put-bucket-versioning \
  --bucket my-bucket \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::123456789:mfa/root-account-mfa-device 123456"
```

MFA Delete cannot be enabled via console — only CLI/API, and only by the root account.

## 6. Replication

### CRR vs SRR

| Property | Cross-Region Replication (CRR) | Same-Region Replication (SRR) |
|---|---|---|
| Destination | Different region | Same region, different bucket |
| Versioning required | Both source AND destination | Both source AND destination |
| IAM role | Required | Required |
| Latency | Higher (cross-region) | Lower |
| Use cases | DR, compliance, latency reduction | Log aggregation, test/prod sync |
| Cost | Data transfer + replication | No cross-region data transfer fee |

### Key Replication Rules

1. **Replication is NOT retroactive** — only new objects after you enable it
2. **Delete marker replication** is optional (must explicitly enable)
3. **Permanent deletes (version deletes) are never replicated**
4. **Chained replication** — A replicates to B, B replicates to C; A does NOT directly replicate to C
5. **Object ownership** — replicated objects are owned by source account by default unless you enable Bucket Owner Override

### Replication Time Control (RTC)

- Guarantees **99.99% of objects replicated within 15 minutes**
- Provides **replication metrics and notifications**
- Additional cost (~$0.015/GB)
- Use for compliance requirements with strict RPO

### Bidirectional Replication

Configure two rules: A→B and B→A. Objects are tagged with a replication flag to prevent infinite loops.

## 7. Lifecycle Rules

### Rule Actions

```
Lifecycle Rule:
  ├── Filter (prefix, tag, size, object age)
  ├── Transition Actions
  │     └── Move to cheaper storage class after N days
  └── Expiration Actions
        ├── Delete current version after N days
        ├── Delete expired delete markers
        ├── Delete non-current versions after N days
        └── Abort incomplete multipart uploads
```

### Minimum Day Constraints

| Transition | Minimum |
|---|---|
| Standard → Standard-IA | **30 days** |
| Standard → One Zone-IA | **30 days** |
| Standard-IA → Glacier | **30 days** after IA transition (60 days total) |
| Standard → Glacier Instant | **90 days** |
| Standard → Glacier Flexible | No minimum |
| Standard → Glacier Deep Archive | No minimum |
| Any → Intelligent-Tiering | No minimum |

### Example Lifecycle Policy (JSON)

```json
{
  "Rules": [{
    "ID": "archive-old-logs",
    "Filter": { "Prefix": "logs/" },
    "Status": "Enabled",
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 90, "StorageClass": "GLACIER" }
    ],
    "Expiration": { "Days": 365 },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}
```

## 8. Security

### Access Control Layers (in evaluation order)

```
Request → [1] Block Public Access → [2] IAM Policy → [3] Bucket Policy → [4] ACL → ALLOW/DENY
```

An explicit DENY at any layer wins. Block Public Access is an account-level or bucket-level override that overrides bucket policies and ACLs.

### Bucket Policy vs ACL vs IAM

| Feature | Bucket Policy | ACL | IAM Policy |
|---|---|---|---|
| Attached to | Bucket (or object) | Bucket or object | IAM identity |
| Cross-account | Yes (no IAM needed on grantee side) | Yes | Needs both IAM + bucket policy |
| Control granularity | High (conditions, IPs, VPCs) | Limited (predefined grants) | High |
| Recommended | Yes | Legacy (AWS recommends disabling ACLs) | Yes |
| Size limit | 20 KB | N/A | 2 KB (inline), 6 KB (managed) |

### Block Public Access Settings

Four independent flags:
1. `BlockPublicAcls` — ignore new public ACLs
2. `IgnorePublicAcls` — ignore all public ACLs (existing too)
3. `BlockPublicPolicy` — reject new public bucket policies
4. `RestrictPublicBuckets` — restrict access even if policy is public

**Default since April 2023**: all four are ON for new buckets.

### Presigned URLs

```bash
# Generate presigned URL valid for 1 hour
aws s3 presign s3://my-bucket/secret-file.pdf --expires-in 3600

# With SDK
import boto3
s3 = boto3.client('s3')
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'file.pdf'},
    ExpiresIn=3600
)
```

- URL inherits the permissions of the signing identity at time of request
- If IAM role is revoked, existing presigned URLs **still work until expiry**
- Max expiry: 12 hours (role-based) or 7 days (user credentials)

### Presigned POST

Used to allow browsers to upload directly to S3 (avoids routing through your server):

```python
response = s3.generate_presigned_post(
    Bucket='my-bucket',
    Key='uploads/${filename}',
    Fields={"Content-Type": "image/jpeg"},
    Conditions=[
        ["content-length-range", 100, 10485760],  # 100B to 10MB
        {"Content-Type": "image/jpeg"}
    ],
    ExpiresIn=3600
)
# Returns: {'url': '...', 'fields': {'key': ..., 'AWSAccessKeyId': ..., ...}}
```

### VPC Endpoints for S3

| Type | Protocol | Cost | Use Case |
|---|---|---|---|
| **Gateway Endpoint** | HTTPS (same) | Free | EC2 in VPC accessing S3 without internet |
| **Interface Endpoint (PrivateLink)** | HTTPS | ~$0.01/hr + $0.01/GB | On-premises via Direct Connect/VPN, cross-VPC |

Gateway endpoint adds a route to the VPC route table. Interface endpoint creates an ENI in the subnet.

```json
// Bucket policy restricting to VPC endpoint only
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
  "Condition": {
    "StringNotEquals": {
      "aws:sourceVpce": "vpce-0123456789abcdef0"
    }
  }
}
```

## 9. Encryption

### Encryption Methods Comparison

| Method | Key Management | Where Encrypted | Performance Impact | Use Case |
|---|---|---|---|---|
| **SSE-S3** | AWS manages key | Server-side | Minimal | Default, simple |
| **SSE-KMS** | KMS CMK, you control | Server-side | KMS API call per op | Audit trail, key rotation, cross-account |
| **SSE-C** | You provide key per request | Server-side | Minimal | You control keys, not KMS costs |
| **DSSE-KMS** | KMS, dual-layer | Server-side (2x) | Double KMS calls | Regulatory (CNSSI 1253) |
| **Client-Side** | You manage entirely | Client-side (before upload) | Your CPU | Data never unencrypted in transit or at rest on AWS |

### SSE-KMS Specifics

```bash
# Upload with SSE-KMS using default S3 KMS key
aws s3 cp file.txt s3://bucket/ --sse aws:kms

# Upload with specific CMK
aws s3 cp file.txt s3://bucket/ \
  --sse aws:kms \
  --sse-kms-key-id arn:aws:kms:us-east-1:123:key/abc-123
```

SSE-KMS caveat: every GET/PUT calls KMS → **KMS request rates apply** (5,500–30,000 requests/sec depending on region). High-throughput workloads need KMS request quota increases.

### Bucket Default Encryption

As of January 2023, all new S3 objects are **encrypted by default with SSE-S3** even if not specified. You can change the default to SSE-KMS.

## 10. CloudFront OAC (Origin Access Control)

Origin Access Control replaced Origin Access Identity (OAI) in 2022.

```json
// Bucket policy granting CloudFront OAC access
{
  "Effect": "Allow",
  "Principal": { "Service": "cloudfront.amazonaws.com" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "StringEquals": {
      "aws:SourceArn": "arn:aws:cloudfront::123456789:distribution/EDFDVBD6EXAMPLE"
    }
  }
}
```

OAC advantages over OAI:
- Supports **SSE-KMS** encrypted buckets (OAI does not)
- Supports **all S3 regions** including new ones
- Supports **POST/PUT requests** (OAI is GET only)

## 11. Access Points

Access Points provide unique hostnames and policies for different apps/teams accessing the same bucket.

```
Bucket: my-data-lake
  ├── Access Point: analytics-ap  → policy allows analytics team, prefix /analytics/
  ├── Access Point: ml-team-ap    → policy allows ML team, prefix /ml/
  └── Access Point: readonly-ap   → GetObject only, any prefix
```

```bash
# Create access point
aws s3control create-access-point \
  --account-id 123456789 \
  --name analytics-ap \
  --bucket my-data-lake \
  --vpc-configuration VpcId=vpc-abc123  # optional VPC restriction
```

Access point ARN: `arn:aws:s3:us-east-1:123456789:accesspoint/analytics-ap`

**Multi-Region Access Points (MRAP)**: single global ARN routes to the lowest-latency replicated bucket.

## 12. S3 Object Lambda

```
Client GET request
    ↓
S3 Object Lambda Access Point
    ↓

```

Use cases:
- Redact PII before returning to analytics system
- Convert data format (XML → JSON)
- Resize images on demand
- Add watermarks

## 13. Event Notifications

### Destination Options

| Destination | Max Delay | Fan-out | Use Case |
|---|---|---|---|
| **SQS** | Seconds | No (1 queue) | Decouple processing |
| **SNS** | Seconds | Yes (fan-out to multiple) | Notify multiple systems |
| **Lambda** | Seconds | No (1 function per rule) | Immediate processing |
| **EventBridge** | < 1 second | Yes (rules + multiple targets) | Complex routing, archiving, replay |

EventBridge is the most powerful option — supports filtering, multiple targets, event replay, and cross-account delivery.

```json
// S3 event notification config for SQS
{
  "QueueConfigurations": [{
    "QueueArn": "arn:aws:sqs:us-east-1:123:my-queue",
    "Events": ["s3:ObjectCreated:*"],
    "Filter": {
      "Key": {
        "FilterRules": [
          { "Name": "prefix", "Value": "images/" },
          { "Name": "suffix", "Value": ".jpg" }
        ]
      }
    }
  }]
}
```

## 14. Performance

### Multipart Upload

| Threshold | Requirement |
|---|---|
| Recommended | Objects > 100 MB |
| Required | Objects > 5 GB |
| Max parts | 10,000 |
| Min part size | 5 MB (except last part) |
| Max part size | 5 GB |

```python
# boto3 multipart upload
import boto3
from boto3.s3.transfer import TransferConfig

config = TransferConfig(
    multipart_threshold=1024 * 25,   # 25 MB
    max_concurrency=10,
    multipart_chunksize=1024 * 25,   # 25 MB
    use_threads=True
)
s3 = boto3.client('s3')
s3.upload_file('large_file.zip', 'bucket', 'large_file.zip', Config=config)
```

### Transfer Acceleration

- Routes uploads through CloudFront edge locations → AWS backbone
- ~60% faster for intercontinental uploads
- Endpoint: `bucket.s3-accelerate.amazonaws.com`
- Additional cost per GB transferred
- Compatible with multipart upload

### Byte-Range Fetches

Download only part of an object — useful for:
- Resumable downloads
- Parallel downloads of large files
- Reading only file headers

```bash
# Download bytes 0-999 (first 1000 bytes)
aws s3api get-object \
  --bucket my-bucket \
  --key large-file.bin \
  --range "bytes=0-999" \
  output.bin
```

### S3 Select

Query objects (CSV, JSON, Parquet) with SQL without downloading the entire object:

```python
response = s3.select_object_content(
    Bucket='my-bucket',
    Key='data.csv',
    ExpressionType='SQL',
    Expression="SELECT * FROM s3object WHERE age > 25",
    InputSerialization={'CSV': {'FileHeaderInfo': 'USE'}},
    OutputSerialization={'JSON': {}}
)
```

Reduces data transfer by up to **98%**. Glacier Select also available for Glacier objects.

## 15. Object Lock (WORM)

Write Once Read Many — prevents deletion or modification.

### Prerequisites
- Must be enabled at bucket creation
- Versioning is automatically enabled

### Retention Modes

| Mode | Who Can Delete | Override |
|---|---|---|
| **Governance** | Users with `s3:BypassGovernanceRetention` permission | Yes, with correct IAM |
| **Compliance** | Nobody (including root) | No — not until retention period expires |

```bash
# Put object with compliance retention
aws s3api put-object-retention \
  --bucket my-bucket \
  --key file.pdf \
  --retention '{"Mode":"COMPLIANCE","RetainUntilDate":"2030-01-01T00:00:00Z"}'
```

### Legal Hold

- Separate from retention periods
- No expiry date
- Can be placed/removed by users with `s3:PutObjectLegalHold` permission
- Use for ongoing litigation

## 16. Requester Pays

The requester (not bucket owner) pays for data transfer and requests:

```json
// Enable Requester Pays on bucket
{
  "RequestPaymentConfiguration": {
    "Payer": "Requester"
  }
}
```

Requester must include `x-amz-request-payer: requester` header. Anonymous requests are not allowed when Requester Pays is enabled.

Use case: public datasets (genomics, weather, etc.) where the dataset owner doesn't want to pay for everyone's downloads.

## 18. Decision Tree — Storage Class Selection

```
What is the access frequency?
│
├─ Accessed frequently (daily/weekly)
│   └─ Standard
│
├─ Access pattern unknown / changing
│   └─ Intelligent-Tiering (if objects > 128 KB and > 30 days old)
│
├─ Accessed monthly or less (infrequent)
│   ├─ Need ms latency?
│   │   ├─ Yes, data is critical/cannot be recreated
│   │   │   └─ Standard-IA (multi-AZ)
│   │   └─ Yes, data CAN be recreated
│   │       └─ One Zone-IA (cheaper, single AZ)
│   └─ Quarterly access OK
│       └─ Glacier Instant Retrieval
│
├─ Archive / rare access (yearly)
│   ├─ Minutes retrieval acceptable?
│   │   └─ Glacier Flexible Retrieval (Expedited: 1-5 min)
│   └─ Hours OK, need cheapest?
│       └─ Glacier Deep Archive ($0.00099/GB/month)
│
└─ Compliance/WORM requirement
    └─ Any Glacier class + Object Lock Compliance mode
```

## 19. Common Patterns

### Pattern 1: Data Lake with Lifecycle Tiering

```
Raw data ingestion → S3 Standard (hot zone)
           ↓ 30 days (lifecycle)
       Standard-IA (warm zone)
           ↓ 60 more days (lifecycle)
       Glacier Flexible (cold zone)
           ↓ 1 year (lifecycle)
       Glacier Deep Archive (frozen)
```

### Pattern 2: Serverless Image Processing Pipeline

```
Mobile App
    │ (upload via presigned POST)
    ▼
S3 Bucket (uploads/)
    │ (S3 Event → Lambda)
    ▼
Lambda: resize + watermark
    │
    ▼
S3 Bucket (processed/)
    │ (CloudFront + OAC)
    ▼
End Users
```

### Pattern 3: Cross-Region Disaster Recovery

```
Primary Region (us-east-1)           DR Region (us-west-2)
S3 Bucket [Versioning ON]  ─── CRR ──→  S3 Bucket [Versioning ON]
      │                                        │
      │ CloudFront OAC                         │ (standby)
      ▼                                        ▼
 Active Traffic                          Failover Target
```

### Pattern 4: Secure Data Distribution

```
Vendor uploads to S3 (via Access Point with prefix restriction)
    ↓
S3 Object Lambda (strips PII)
    ↓
Analytics team Access Point (read-only)
    ↓
Athena / Redshift Spectrum queries
```

### Pattern 5: Compliance Archive

```
Audit logs → S3 Glacier Deep Archive
  + Object Lock (Compliance mode, 7-year retention)
  + MFA Delete enabled
  + CloudTrail logging ON
  + Bucket policy: DENY s3:DeleteObject*
  + Replication to second account (extra protection)
```

## 20. Gotchas

### Exam Traps

| Gotcha | Reality |
|---|---|
| "S3 eventual consistency" | FALSE since Dec 2020 — S3 is now **strongly consistent** |
| CRR works without versioning | FALSE — versioning must be enabled on **both** source and destination |
| Lifecycle can transition directly from Standard to One Zone-IA | TRUE but must wait 30 days |
| Presigned URL with expired role works | TRUE until the URL itself expires |
| MFA Delete can be enabled in console | FALSE — CLI only, root account only |
| Glacier objects instantly accessible | Only Glacier **Instant** Retrieval; Flexible = 3-5 hours |
| S3 supports POSIX operations (rename, append) | FALSE — no rename, no append, no partial write |
| CRR replicates existing objects | FALSE — only new objects after rule creation (use S3 Batch Replication for existing) |
| Delete replication included in CRR by default | FALSE — delete marker replication must be explicitly enabled |

### Production Pitfalls

1. **KMS throttling**: High-throughput SSE-KMS workloads hit KMS API limits. Request quota increases or use SSE-S3.

2. **Lifecycle 30-day minimum**: You pay for the minimum storage duration even if you delete early. Uploading 1 KB to Standard-IA and deleting after 1 day still charges 30 days.

3. **Multipart upload orphans**: Failed uploads leave parts that cost money. Always configure `AbortIncompleteMultipartUpload` lifecycle rule.

4. **Versioning cost explosion**: Enabling versioning on a bucket with frequent writes accumulates all old versions — add noncurrent version expiration lifecycle rules.

5. **S3 is not a filesystem**: Cannot do `mv` (it's copy + delete), cannot append to files, no atomic rename. Applications expecting filesystem semantics will break.

6. **Replication doesn't include object metadata**: By default, replicas are owned by source account, not destination. Use Bucket Owner Override to change ownership.

7. **EventBridge vs S3 Event Notifications**: Only EventBridge supports filtering by object metadata, size, and other advanced criteria. For simple prefix/suffix filtering, either works.

8. **Object Lock requires enabling at bucket creation**: You cannot enable Object Lock on an existing bucket.

## 21. Hands-On Lab (Free Tier)

### Lab: S3 Versioning, Lifecycle, and Encryption

**Estimated cost**: $0 (stays within free tier)
**Time**: 30 minutes

#### Step 1: Create Bucket with Versioning

```bash
# Create bucket
aws s3api create-bucket \
  --bucket my-s3-lab-$(date +%s) \
  --region us-east-1

# Store bucket name
BUCKET=my-s3-lab-<timestamp>

# Enable versioning
aws s3api put-bucket-versioning \
  --bucket $BUCKET \
  --versioning-configuration Status=Enabled

# Verify
aws s3api get-bucket-versioning --bucket $BUCKET
```

#### Step 2: Upload Objects and Test Versioning

```bash
# Create test file and upload multiple versions
echo "version 1" > test.txt
aws s3 cp test.txt s3://$BUCKET/test.txt

echo "version 2" > test.txt
aws s3 cp test.txt s3://$BUCKET/test.txt

echo "version 3" > test.txt
aws s3 cp test.txt s3://$BUCKET/test.txt

# List all versions
aws s3api list-object-versions --bucket $BUCKET

# Delete object (creates delete marker)
aws s3 rm s3://$BUCKET/test.txt

# Verify object appears gone
aws s3 ls s3://$BUCKET/

# List versions again — delete marker is there
aws s3api list-object-versions --bucket $BUCKET

# Restore by deleting the delete marker
DELETE_MARKER_ID=$(aws s3api list-object-versions \
  --bucket $BUCKET \
  --query "DeleteMarkers[?Key=='test.txt'].VersionId" \
  --output text)

aws s3api delete-object \
  --bucket $BUCKET \
  --key test.txt \
  --version-id $DELETE_MARKER_ID

# Object is back
aws s3 ls s3://$BUCKET/
```

#### Step 3: Configure Lifecycle Rule

```bash
# Create lifecycle config file
cat > lifecycle.json << 'EOF'
{
  "Rules": [{
    "ID": "expire-old-versions",
    "Filter": {},
    "Status": "Enabled",
    "NoncurrentVersionExpiration": {
      "NoncurrentDays": 30
    },
    "AbortIncompleteMultipartUpload": {
      "DaysAfterInitiation": 7
    }
  }]
}
EOF

aws s3api put-bucket-lifecycle-configuration \
  --bucket $BUCKET \
  --lifecycle-configuration file://lifecycle.json

# Verify
aws s3api get-bucket-lifecycle-configuration --bucket $BUCKET
```

#### Step 4: Configure Encryption

```bash
# Set default encryption to SSE-KMS
aws s3api put-bucket-encryption \
  --bucket $BUCKET \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms"
      },
      "BucketKeyEnabled": true
    }]
  }'

# Upload object and verify encryption
echo "encrypted content" > encrypted.txt
```

#### Step 6: Enable Event Notification to SQS

```bash
# Create SQS queue
QUEUE_URL=$(aws sqs create-queue --queue-name s3-events --query QueueUrl --output text)
QUEUE_ARN=$(aws sqs get-queue-attributes \
  --queue-url $QUEUE_URL \
  --attribute-names QueueArn \
  --query "Attributes.QueueArn" --output text)

# Set SQS policy to allow S3
aws sqs set-queue-attributes \
  --queue-url $QUEUE_URL \
  --attributes "{
    \"Policy\": \"{\\\"Version\\\":\\\"2012-10-17\\\",\\\"Statement\\\":[{\\\"Effect\\\":\\\"Allow\\\",\\\"Principal\\\":{\\\"Service\\\":\\\"s3.amazonaws.com\\\"},\\\"Action\\\":\\\"sqs:SendMessage\\\",\\\"Resource\\\":\\\"$QUEUE_ARN\\\"}]}\"
  }"

# Configure S3 event notification
aws s3api put-bucket-notification-configuration \
  --bucket $BUCKET \
  --notification-configuration "{
    \"QueueConfigurations\": [{
      \"QueueArn\": \"$QUEUE_ARN\",
      \"Events\": [\"s3:ObjectCreated:*\"]
    }]
  }"

# Upload a file and check SQS for the event
echo "trigger event" > event-test.txt
aws s3 cp event-test.txt s3://$BUCKET/event-test.txt

sleep 5
aws sqs receive-message --queue-url $QUEUE_URL
```
